# 0.1 固定实例输入与输出约定

文档版本：1.1.0；更新日期：2026-10-22（America/Los_Angeles）。信息范围与基本约定已由用户采用；以下 JSON 键名与日志布局是落地示例，尚未作为实现接口冻结。

返回 [总览](00-START-HERE.md)；模型字段见 [字段表](04-MODEL-FIELDS.md)；运行状态与重跑见 [07](07-STATE-OWNERSHIP.md)。

## 1. 输入的三个部分

1. 资源环境：有哪些移动设备、边缘服务器、云服务器。
2. 工作流实例：ID、所属设备、到达时间、任务、依赖、每个任务在各资源上的时间参数。
3. 运行配置：选择哪条路由/排序规则、读取哪个实例、是否输出日志。配置与实例分开保存。

固定到达时刻仍能表达动态到达。实例文件可以预先包含未来工作流，但调度规则只能获得已经到达的工作流状态。

## 2. 已采用的基本约定

| 项目 | 约定 |
| --- | --- |
| 初始资源 | M0、E0、C0 各一个；全部以列表管理，可扩展数量 |
| 类型 | 明确保存 MOBILE、EDGE、CLOUD，不仅根据名称前缀判断 |
| 时间单位 | 秒 |
| 时间范围 | 到达时间、上传/下载时间大于等于 0；计算时间大于 0；均为有限数值 |
| 工作流 ID | 全局唯一，建议数值 0、1、2…；ID 顺序不代表到达顺序 |
| 任务 ID | 在工作流内唯一；通过工作流 ID＋任务 ID 定位；手工例子可用 A、B |
| 资源 ID | 展示/文件 ID 全局唯一，例如 M0、E0、C0 |
| 数量 | 从资源、工作流、任务列表长度取得；若另有数量声明，必须校验一致 |
| 依赖 | 工作流内部有向边；节点存在；无自依赖、重复边和环 |
| 候选资源 | 所属移动设备（允许本地计算时）＋全部边缘服务器＋全部云服务器 |
| 参数完整性 | 每个合法候选都提供完整三项时长；缺少参数报错，不当作 0 或静默减少候选 |
| 设备资格 | 移动设备只能执行属于自身的工作流；输入中的所属设备必须存在 |
| 本地通信 | 本地上传、下载时间为 0 |
| 初始状态 | 时钟 0；队列为空；任务标记为假，预约为 None；全部输入先在 pending_arrivals，由到达事件激活 |
| 执行 | 非抢占；资源同一时刻处理一个任务；下载计入资源占用 |
| 结束 | 全部输入工作流完成后正常结束；事件耗尽但任务未完成时报异常 |
| 统计 | 无 warm-up，全部输入工作流参与 makespan |

若将来设置 M0 不允许本地计算，则该设备的本地选项不生成；当前配置为允许本地计算。输入模式仍以当前允许的候选集合检查完整性。

每个集合保留其约定的遍历顺序，不能无意经 set 或排序改变。候选构建顺序和事件平分处理仍需在接口/事件设计中明确；Java 默认候选为本地、边缘、云。

## 3. 依赖的存储

建议每条边保存一对任务 ID，第一个为前驱、第二个为后继：

```json
{
  "dependencies": [["A", "B"], ["A", "C"], ["B", "D"], ["C", "D"]]
}
```

文件只维护这一份边集合。加载时建立 Task.parents 与 Task.children，并让它们引用同一组任务对象。0.1 先验收单任务和链式；复杂 DAG 留给 0.2，不应宣称已验证。

## 4. 完整实例示例

这是一个供设计和后续编码使用的完整 JSON 示例，不是已经实现或运行的接口。用户已讨论的 E0 时间为手算基准；本地和 C0 数值是为了补全候选而给出的示例值。

```json
{
  "time_unit": "s",
  "resources": [
    {"id": "M0", "type": "MOBILE", "can_process_tasks": true},
    {"id": "E0", "type": "EDGE"},
    {"id": "C0", "type": "CLOUD"}
  ],
  "workflows": [
    {
      "id": 0,
      "owner_device_id": "M0",
      "release_time": 0.0,
      "tasks": [
        {
          "id": "A",
          "execution_times": {
            "M0": {"upload_time": 0.0, "processing_time": 10.0, "download_time": 0.0},
            "E0": {"upload_time": 2.0, "processing_time": 3.0, "download_time": 1.0},
            "C0": {"upload_time": 5.0, "processing_time": 1.0, "download_time": 4.0}
          }
        },
        {
          "id": "B",
          "execution_times": {
            "M0": {"upload_time": 0.0, "processing_time": 12.0, "download_time": 0.0},
            "E0": {"upload_time": 1.0, "processing_time": 4.0, "download_time": 2.0},
            "C0": {"upload_time": 4.0, "processing_time": 2.0, "download_time": 3.0}
          }
        }
      ],
      "dependencies": [["A", "B"]]
    }
  ]
}
```

暂不要求同时提供工作量、数据量、计算速率和带宽。后续引入“由原始参数计算时长”的输入模式时，应明确该模式与直接给定时长模式的关系，不允许两套相互矛盾的参数同时决定一次运行。

## 5. 运行规则与时间校验分开

正式基线先采用源码 FCFS 路由＋FCFS 排序。为校验远程时间，可以在调试配置中固定选择 E0：

```json
{
  "instance": "data/cases/chain_remote.json",
  "routing_rule": {"kind": "fixed_resource", "resource_id": "E0"},
  "sequencing_rule": {"kind": "fcfs"},
  "trace_enabled": true
}
```

`fixed_resource` 是拟实现的调试选择方式，不代表原 Java 的某个论文基准算法，也不是已经存在的命令。不能通过故意遗漏 M0/C0 的时间参数来强制走 E0。

FCFS 的含义已核对：路由比较资源 available_time 的原值；排序比较任务所属工作流 release_time；分数小者优先，平分行为见源码语义文档。因此切换回 FCFS 后应重新手算预期，不沿用固定 E0 的 13。

## 6. 输出内容

| 输出 | 必要信息 |
| --- | --- |
| 运行结果 | 正常完成/异常、完成工作流数、makespan；异常时不能伪装成功结果 |
| 工作流记录 | ID、所属设备、release_time、completion_time、flow_time |
| 任务时间记录 | 工作流 ID、任务 ID、选定资源、派发、到达、开始、计算结束、任务完成时刻 |
| 决策日志 | 时间、ROUTING/SEQUENCING、候选与遍历次序、候选分数、最终选择 |
| 事件日志 | 实际处理序号、时间、事件类型、涉及对象、状态变化及新事件 |
| 资源轨迹 | 队列与缓存变化、可用时间、待开始预约，以及各资源实际开始与完成记录 |

任务时间记录可概念化为以下列。具体输出格式（JSON、JSONL 或 CSV）和键名仍待接口设计：

```text
workflow_id, task_id, resource_id, dispatch_time, arrival_time,
start_time, compute_finish_time, finish_time
```

事件序号记录实际处理顺序，用于诊断；它不自动成为事件堆的平分排序键。规则评分会覆盖 TaskOption.priority，日志应在决策时保存当时的数值快照。

Execution 建立时已有确定计划时间，但不表示开始/完成事件已经触发。若中间日志输出这些时间，应标明其计划含义；任务最终时间记录中的实际开始、完成，只能在对应事件触发后确认。失败运行不得用预测 finish_time 填充未发生的完成事实。具体键名和布局仍待接口设计。

工作流任务会交错、并行处理，因此不设一个能完全表达运行过程的单一“工作流调度序列”。分别记录到达顺序、派发顺序、各资源执行顺序和完成顺序。

## 7. 时间公式与手算

设 r 为满足依赖并路由的时间，a 为上传完成时间，s 为实际开始时间：

```text
a = r + upload_time
s >= a，具体由资源状态和排序决定
compute_finish_time = s + processing_time
finish_time = compute_finish_time + download_time
queue_waiting_time = s - a
```

只有完成事件触发时才把 Task.completed 置为 True。资源占用到 finish_time；后继在前驱完成后才可能释放。当前源码中，即便后继选择同一远程服务器，也继续采用对应上传下载时间。

固定 E0 的示例过程：

| 时间 | 预期动作 |
| ---: | --- |
| 0 | W0 到达，A 派发至 E0，开始上传 |
| 2 | A 到达并开始计算 |
| 5 | A 计算结束；这是记录的时间点，不要求新增一种事件 |
| 6 | A 完成且资源释放；B 派发并开始上传 |
| 7 | B 到达并开始计算 |
| 11 | B 计算结束；同样可作为派生记录 |
| 13 | B 完成，W0 完成 |

```text
makespan = max(全部工作流 completion_time) - min(全部工作流 release_time)
示例：13 - 0 = 13
```

目前这是手算结果，没有 Java 或 Python 运行通过的证据。

## 8. 后续随机实例与固定输入的衔接

- 固定文件加载和随机生成最终提供一致的内部输入描述。
- 随机生成可直接产生内存对象；需要复用时再导出，不必每到达一个工作流就写一次文件。
- Java 当前使用 DAX 模板＋随机参数；任意随机 DAG 是另一条实例来源，不可无记录地替换基线。
- 到达间隔为指数分布。增加设备时，需明确到达率按设备还是按系统给出。
- 全局工作流 ID 按生成顺序分配；makespan 不依赖 ID 顺序。
- seed 相同不保证跨语言实例相同；先通过固定或导出输入对照。

## 9. 状态归属设计对输入输出的补充

- 本轮不新增必须由 JSON 提供的运行状态字段；pending_start、标记、缓存、集合、执行索引与事件队列均由程序初始化。
- release_time=0 的输入保持有效；初始化时即使它等于当前时钟，也要经过到达事件才可供路由。未来实例不能经完整内部索引泄漏给规则。
- 固定重跑从同一 InstanceSpec 新建运行对象、事件和日志。输入内容、遍历顺序与运行配置相同时，应复现同一既定事件策略的结果；目前尚未运行验证，也未冻结全部平分策略。
- 每轮输出独立记录正常/异常状态。计数由 SystemState 集合或模型记录派生；资源完成任务数与设备发布工作流完成数分别解释。
- 任务时刻、决策分数和日志只是本轮事实/快照的输出，不作为另一套可修改的调度状态。全部输入完成后仍按第 7 节计算 makespan。
