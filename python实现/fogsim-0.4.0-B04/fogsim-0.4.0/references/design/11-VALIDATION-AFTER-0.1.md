# 0.1 代码实现后的验证清单与证据要求

- 项目：Xu 等（2023）雾计算调度 Java→Python 复现。
- 文档版本：1.0.0；日期：2026-10-22。
- 性质：**实现后的验证计划。本文没有执行模拟器，所有运行项目均为“待验证”，没有验收通过结论。**
- 依据：00—07 文档集 1.1.0、[08 事件读写表](08-EVENT-READ-WRITE.md)、[09 最终接口第一版](09-INTERFACES.md)、[10 同时刻策略第一版](10-SIMULTANEOUS-EVENT-POLICY.md)。
- 目标：说明 0.1 写完后先验证什么、怎样判断通过、保留什么证据，以及哪些项目属于后续 0.2，避免把“设计完成”误写成“已与 Java 等价”。

## 1. 验证范围与完成口径

| 层次 | 检查什么 | 与版本验收的关系 |
| --- | --- | --- |
| A：Python 0.1 必要验证 | 固定输入、规范对象、规则/状态组件、单任务和链式完整生命周期、结果、失败和重跑 | 0.1 功能完成的必要条件 |
| B：Java 局部参考验证 | 指定 JDK 的比较器/堆 oracle、源码局部操作对照、Java 固定输入准备 | 0.1 后可立即做；支持具体兼容声明，不等同于完整模拟对照 |
| C：0.2 集成及行为对照 | 分叉汇合、多个工作流竞争、复杂同刻事件、Java/Python 相同固定输入逐事件逐决策对照 | 维持原 0.2 主验收范围，不提前要求 0.1 全部通过 |
| D：以后阶段 | DAX/随机生成、RNG/seed 对齐、完整 GP 与训练统计 | 不属于 0.1 验收 |

0.1 不以完整竞争/DAG 集成作为通过条件，但已经实现的队列、比较器和预约入口仍须做必要局部检查。单链没有真正排队，不能靠它声称队列缓存或预约竞争已覆盖。

“Java/Python 行为等价性”也不只是过去列出的几个尚待验证点：它是同输入、同配置下的整体证据，包含已静态核对并实现的主流程，以及显式 Python 调整的边界。源码事实不用等 Python 才能阅读确认；某个实现是否遵守事实、保护是否改变可达路径，则需要代码和运行证据。

## 3. A1：输入、初始化与对象引用

以下均为 0.1 必要检查；当前状态全部待验证。

| 编号 | 验证项目 | 通过标准 |
| --- | --- | --- |

| IN-02 | ID 与所属关系 | 资源展示 ID 唯一、工作流全局整数 ID 唯一、任务在工作流内唯一；所属设备存在；任务复合键可区分不同工作流中的同名任务 |

## 4. A2：查询、评分和选择

| 编号 | 验证项目 | 通过标准 |
| --- | --- | --- |
| RD-01 | 纯就绪查询 | 仅 active 工作流；按任务顺序筛未派发、未完成、前驱全完成；返回原 Task 引用 |
| RD-02 | 查询无副作用 | 调用前后 priority、ready_time、标记、队列、缓存、预约、执行记录不变；规则调用计数不增加 |
| RD-03 | 空列表语义 | 无可派发任务返回 []；“所有未完成任务已派发/仍执行”时不登记工作流完成 |
| SEL-01 | FCFS 路由 | 分数等于资源 available_time 原值，允许小于当前时钟；不改成 max(clock,available_time) |
| SEL-02 | FCFS 排序 | 分数等于所属工作流 release_time，不是 option.ready_time 或入队时间 |
| SEL-03 | 平分层次 | 小分数→早 release→小 owner 设备数值 ID→小 workflow ID；完全平分保留遍历先出现项，不额外比较 task/resource ID |
| SEL-04 | 特殊分数局部 | priority 的 -0/+0、NaN、无穷大按 Double.compare；与事件有限时间要求区分 |
| SEL-05 | 调用与修改职责 | priority 函数只读；selector 按候选顺序逐项评分并覆盖 priority；只有一项也评分；返回原对象 |
| SEL-06 | 队列选择不出队 | choose_next 评分时队列/缓存包含选中项，函数返回后成员未删；由统一出队入口删除 |
| SEL-07 | 空候选错误 | ready 查询为空正常；选择空候选明确错误，无任意默认资源 |
| SEL-08 | 路由次数 | 到达时每入口一次；完成释放后继 A、B 时为 A、B、A、B，第二轮后才统一派发，不改成 A、A、B、B |
| SEL-09 | 评分快照 | 后一次 priority 覆盖不会改写历史日志；日志保留候选原顺序和两轮标记 |

0.1 单链可以验证一个后继的两次评分；两个后继的整批顺序用选择/流程局部测试检查，完整分叉汇合运行仍留 0.2。

只读 tuple 只保护成员集合与顺序，不保护对象字段。测试应让违规评分尝试修改状态时能被接口约束或检查发现；不要仅验证 candidates 的类型是 tuple。

## 5. A3：事件处理和状态归属

### 5.1 时间与任务字段

| 编号 | 验证项目 | 通过标准 |
| --- | --- | --- |
| EV-01 | 唯一时钟 | 只有 Engine 在 trigger 前推进 clock；事件观察到 clock==event.time；不回退、不做容差合并、不写 MAX_VALUE 惩罚 |
| EV-02 | 派发时机 | 安排 TaskVisit 时 dispatched=True；上传期间已防重复派发；不等 Visit 才设置 |
| EV-03 | 完成时机 | 只在 ProcessFinish 实际触发时 completed=True；compute_finish 不提前完成、不增加第五种事件 |
| EV-04 | 入口 ready_time | 工作流到达时按入口顺序，先设置该入口全部选项为 release，再路由派发 |
| EV-05 | 选中项 ready_time | TaskVisit 只把实际选项改为到达 t；后继未选项仍保持原值，不能统一刷新成当前时钟 |
| EV-06 | 开始与后继 | Start 更新资源时间并安排 Finish；Finish 先登记任务完成，再处理队列，再查询/路由后继，最后才可能登记工作流 |
| EV-07 | 新事件 | 只 emit 入队，不直接 trigger；后继上传从当前完成 t+UT 起算，同一远程服务器也不省略 UT/DT |

### 5.2 等待队列与两个缓存

| 编号 | 验证项目 | 通过标准 |
| --- | --- | --- |
| Q-01 | 入队成员 | 只含已上传到达、已派发未开始的选项；不能含上传中、已预约、执行中或已完成项 |
| Q-02 | 入队缓存 | 增加 PT 和 (PT+UT+DT)，按源码运算顺序；UT 已发生仍包含在该特征定义中，不代表再上传 |
| Q-03 | 出队身份/顺序 | 移除指定原对象，其他项顺序不变；不存在或重复项报错；出队与缓存同时维护 |
| Q-04 | Server 空队 | 移除最后一项后两缓存明确归 0，空队 getter 返回 0 |
| Q-05 | MobileDevice 空队 | 始终做减法，getter 直接返回缓存；允许浮点残差，不统一钳零/重求和 |
| Q-06 | 缓存数值检查 | 非空时与按时长求得的量在验证容差内相符，同时检查操作序列；不能只靠重新求和相同就忽略源码增减差异 |
| Q-07 | 排序前后 | Finish 中即使队列只有一项仍先评分；出队后才进入后续路由，路由看到缩短后的队列和缓存 |

至少准备整数时长例子核对精确值，以及如 0.1、0.2、0.3 组成的浮点例子暴露加减顺序和资源类型差异。不能把 MobileDevice 的合法残差判成失败后偷偷改实现。

### 5.3 Execution 与预约

| 编号 | 验证项目 | 通过标准 |
| --- | --- | --- |
| EX-01 | 正式执行创建 | 仅接受确定开始安排后创建；busy 分支试算不进入执行索引，不出现幽灵 Execution |
| EX-02 | 时间公式 | compute=s+PT，finish=compute+DT，保持加法顺序；含下载占用；正式计划字段不再改写 |
| EX-03 | 索引/引用 | 每任务最多一个执行；executions_by_task、pending_start、开始/完成事件及完成历史引用同一对象 |
| RES-01 | 直接开始保护 | Visit 观察 avail<=t 且无 pending 才预约；预约之后、Start 之前另一到达不得再预约同资源 |
| RES-02 | 队列续接保护 | 从队列选择后出队，按 max(avail,t) 接受安排；相同 pending 防重检查覆盖此路径 |
| RES-03 | 预约期间时间 | pending 建立后 avail 仍是旧值；Start 触发才更新至该执行 finish；上传阶段不建 pending |
| RES-04 | 匹配清除 | Start 只清自己的预约；错误 Execution/重复 Start 明确失败，不能清掉其他安排 |
| RES-05 | 旧完成不破坏新状态 | 已有同刻 Start 更新 avail 或建立别项预约时，旧 Finish 不重写 avail、不清别项 pending、不重复安排队列项 |
| RES-06 | 占用区间 | 每资源实际区间 [start,finish) 含 DT、无重叠；允许前项 finish==后项 start |

RES-01 的关键观察点是“接受安排以后、开始事件以前”，不能等完整运行结束才看队列是否为空。可构造局部处理序列验证，不必将完整多工作流同刻竞争提前变成 0.1 主验收。

开始事件可先于同刻旧完成事件，因此不要断言任何瞬间“所有未写完成标记的已开始任务最多一个”。物理占用用区间检查，事件记账用阶段与身份检查。

### 5.4 工作流与全局一致性

| 编号 | 验证项目 | 通过标准 |
| --- | --- | --- |
| WF-01 | 完成记录 | 仅实际 Finish 追加，每任务一次，Task.completed、Resource.completed_task_count 与记录同步 |
| WF-02 | 空查询但未完成 | 仍有上传/排队/执行任务时不注册工作流；不能用 [] 代替 all_done |
| WF-03 | 完成登记 | 全部任务完成后，completion_time 为本次实际完成时刻；active→completed 一次；completion_registered=True |
| WF-04 | 重复处理 | 重复任务完成报错且不再追加/计数；已一致登记工作流再次 register 返回 False；标记与集合矛盾报错 |
| WF-05 | 集合分区 | pending/active/completed 两两互斥并覆盖全部输入；只有到达事件激活，只有完成登记迁移到 completed |
| WF-06 | 派生统计 | completed 蕴含 dispatched；所有资源完成任务数之和=工作流完成执行数之和=已完成任务数；完成工作流数从集合得到 |
| WF-07 | 无训练筛选 | 0.1 无 warm-up，全部固定输入参与统计；不误抄 Java 训练窗口、throughput 条件或清空拓扑 |

不变量在每个完整事件处理后的稳定观察点检查。操作内部的多字段提交间隙不是调度器可以读取的额外事件边界。

## 6. A4：同时刻与事件管理的必要组件检查

本节覆盖 0.1 已使用的组件；大型竞争实例仍是 0.2。

| 编号 | 检查 | 通过标准 |
| --- | --- | --- |
| EQ-01 | 不同时间 | 小时间先；近似相等但实际不同的时间不合并；派生时刻非法明确错误 |
| EQ-02 | 不同类型同刻 | JA<PS<TV<PF，四乘四比较矩阵与 10 一致 |
| EQ-03 | 同类返回 | JA 按 workflow ID，相同 -1；PS/TV 同类 0；PF 本地在服务器前，再按相应编号，相同 +1 |
| EQ-04 | 无新增键 | 兼容主线不追加任务/资源字符串 ID、enqueue_seq 或 processed_event_count 平分键 |
| EQ-05 | 暂存归并 | 按设备固定列表逐堆 poll，再逐项 offer 全局；不按数组迭代、不稳定重排、不直接全局 push |
| EQ-06 | 每事件重新竞争 | 新同刻 Start 经暂存归并后能先于尚未处理的 Visit 竞争；不预取全部同刻事件 |
| EQ-07 | owner 与暂存位置 | ctx.emit 进入当前处理设备暂存堆，新事件 owner 仍属所执行任务；局部检查可以用两个设备对象 |
| EQ-08 | 队列判空 | has_pending 同时检查两层但不归并；pop_next 全空才 None；遗漏暂存事件不能导致过早结束 |
| EQ-09 | 堆操作审查 | offer/poll 比较方向、相等时左右孩子选择与指定参考源码一致；不以 heapq 包装“看起来一样”代替证据 |

EQ-03 中异常分支可以使用合成事件对独立测试，标明是比较器分支覆盖。它不表示这些输入能通过固定实例合法性校验，也不证明正常工作流能触发该分支。

若 B 层 Java 堆 oracle 尚未完成，可报告“Python 组件检查通过，目标 JDK 堆序列兼容待验证”；不可直接写“Java 队列等价已通过”。

## 7. A5：三组可手算的完整运行

以下是后续测试的**预期**，不是已运行结果。全部保留 M0/E0/C0 的合法候选参数；用调试固定资源规则选择目标，不能通过漏掉候选参数强制选路。

### 7.1 CASE-L：单任务本地

这是补充的最小验收实例：W0 release=0，单任务 A，在 M0 上 PT=3、UT=DT=0。其他合法资源参数完整且有限；使用固定 M0 调试规则，或确保当前 FCFS 初始平分按候选顺序选 M0。

| 项目 | 预期 |
| --- | --- |
| 四事件 | JA(0)、TV-A(0)、PS-A(0)、PF-A(3) |
| A 时间 | dispatch=0，arrival=0，start=0，compute_finish=3，finish=3 |
| 工作流 | completion=3，flow_time=3 |
| 系统 | final_clock=3，makespan=3，完成工作流数=1 |
| 标记/记录 | 派发后 dispatched=True；PF 前 completed=False；最终一条完成 Execution，工作流登记一次 |

再增加 release=5 的变体：实际完成/最终时钟为 8，flow_time=3，makespan=8-5=3。此例检查 makespan 不是直接取 final_clock，也不是随意从 0 开始相减。

### 7.2 CASE-R：03 中固定 E0 的 A→B

沿用 03 完整实例，路由配置为调试固定 E0，排序 FCFS：

| 任务 | UT | PT | DT | dispatch | arrival | start | compute_finish | finish |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| A | 2 | 3 | 1 | 0 | 2 | 2 | 5 | 6 |
| B | 1 | 4 | 2 | 6 | 7 | 7 | 11 | 13 |

预期 W0 completion=13，flow_time=13，makespan=13；实际事件共 7 条：JA(0)、TV-A(2)、PS-A(2)、PF-A(6)、TV-B(7)、PS-B(7)、PF-B(13)。5 和 11 不是额外事件。

| 稳定观察点 | 关键字段预期 |
| --- | --- |
| JA(0) 后 | W0 active；A 已派发未完成，尚无正式 Execution 或 pending；A 所有选项 ready=0 |
| TV-A(2) 后 | A 的 E0 选项 ready=2，其余仍 0；exA 已登记且为 E0.pending_start；E0.available_time 仍 0 |
| PS-A(2) 后 | pending=None；E0.available_time=6；A 未完成，完成列表为空 |
| PF-A(6) 后 | A 完成，完成列表为 exA；B 已按两轮路由后派发；B 全部选项 ready 仍 0；W0 未登记，E0.available_time=6 |
| TV-B(7) 后 | B 的 E0 选项 ready=7；exB 已登记且为 pending；available_time 仍 6 |
| PS-B(7) 后 | pending=None；available_time=13；B 仍未完成 |
| PF-B(13) 后 | 完成列表为 exA/exB；E0 完成任务数=2；W0 completion=13、registered=True，位于 completed；available_time=13 |

本例没有真实等待队列：缓存一直为零，不能当作 Q-02～Q-07 已全部覆盖。决策调用应为入口 A 一次路由、后继 B 两次路由；无排序调用，因为完成时队列为空。

### 7.3 CASE-F：同一完整实例改用源码 FCFS

使用 03 的完整数值，不换输入，仅改回 FCFS 路由＋FCFS 排序。本节为本次新增手算预期，尚待程序验证：

| 决策时刻 | available_time：M0/E0/C0 | 预期选择与原因 |
| ---: | --- | --- |
| 0，路由 A | 0 / 0 / 0 | 全部平分，候选顺序保留 M0；A 本地 PT=10，完成于 10 |
| 10，路由 B（两轮） | 10 / 0 / 0 | E0/C0 分数更小且彼此平分，保留先出现的 E0 |

| 任务 | 资源 | dispatch | arrival | start | compute_finish | finish |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| A | M0 | 0 | 0 | 0 | 10 | 10 |
| B | E0 | 10 | 11 | 11 | 15 | 17 |

预期 W0 completion=17，makespan=17。固定 E0 的 13 与此处 17 对应不同运行规则，不应要求两者一样。此例同时检查 FCFS 比较资源旧 available_time，而不是 PT 最短、完成时间最短或 max(clock,available_time)。

## 8. A6：结束、失败、日志和固定重跑

| 编号 | 项目 | 通过标准 |
| --- | --- | --- |
| RUN-01 | 正常结束 | 全部固定输入完成才成功；完成数和记录一致；makespan=max(completion)-min(release) |
| RUN-02 | 事件耗尽 | 注入“尚未完成但两层事件全空”的状态，明确 FAILED 及原因，不返回成功指标 |

| LOG-02 | 不可变快照 | 后续评分/队列修改不改历史日志；日志用 ID/数值快照，不保存活模型引用作为历史 |

| RE-02 | 重跑初态 | 每轮所有运行对象、事件、队列、索引、priority、ready_time、缓存、标记、预约、处理序号、日志重新建立 |
| RE-03 | 无旧引用 | 第二轮对象不引用第一轮 Task/Resource/Execution；第一轮结果不会被第二轮修改 |
| RE-04 | 固定与随机分开 | 固定重跑不消费随机流；没有偷偷调用 Java 式随机生成下一工作流或把 seed 重置当作模型重置 |

### 10.1 什么要相同，什么允许结构不同

| 对照对象 | 比较方式 |
| --- | --- |
| 稳定对象 | workflow/task/resource ID、候选顺序、owner/服务器编号精确一致 |
| 事件 | 在相同稳定边界比较类型、时间和任务/资源；实际序列先比较，不能用时间容差重新配对错序事件 |
| 决策 | 同次调用的特征值、分数、选择、轮次；保留 A、B、A、B 两整轮评分 |
| 状态 | 任务标记、ready_time、available_time、队列、缓存、完成记录及数量；在对应事件处理前后比较 |
| 结构调整 | Java 的完成事件列表与 Python 的 Execution 列表按任务和时间字段对应；不要求类名和对象数量相同 |
| 构造副作用迁移 | 比较提交后/事件边界的可见状态，不要求 Python 纯构造与 Java TaskVisit 构造的中间状态逐句一样 |
| Python 新保护 | 记录 pending_start/去重的前置条件与结果；若原 Java 出现差异，判断可达原因并明确报告，不直接写完全等价 |
| 纯查询次数 | 无副作用的重复扫描可减少；有 priority 修改的评分调用次数不能无记录减少 |

### 10.2 第一个差异如何定位

依次检查：输入与配置 → ID/顺序映射 → 当前可见状态/特征 → 候选分数 → 平分选择 → 派发/预约提交 → 生产设备与暂存 → 堆操作与下一事件 → 稳定状态 → 最终指标。

找到第一处差异就保存两侧快照和最小实例，先解释该差异，再看其后结果。不要只因最终 makespan 一样就忽略早已分叉的轨迹，也不要在对照器中任意排序日志来消除差异。

## 11. 浮点数与比较标准

本节是验证约定，不改变 Java 算法。建议 0.1 秒单位小实例先采用 `abs_tol=1e-9`、`rel_tol=1e-12`，记录到测试配置中：

`abs(a-b) <= max(abs_tol, rel_tol * max(abs(a),abs(b)))`

| 对象 | 标准 |
| --- | --- |
| ID、类型、标记、成员、选择、事件序列、调用次数 | 精确一致，不使用数值容差 |
| 手算整数时间案例 | 应精确达到表中值；容差仅处理实现/导出细节，不掩盖整秒差异 |
| 时间、分数、缓存等浮点对照 | 原始值完整保留；用上述配置报告误差；异常时检查运算顺序而不是自动放宽容差 |
| 事件排序/资源分支 | 实际算法仍精确比较；不使用验证容差决定同刻、是否忙或谁优先 |
| priority 的 NaN/+0/-0 | 按 Double.compare 的专门语义测试，不能仅靠 abs(a-b) |
| Server 空队归零 | 应明确为 0；不能因容差很宽就允许未做归零 |
| MobileDevice 空队残差 | 按原增减序列和原 getter 检查；不要求统一归零 |

若比较器输入极接近，需要另保留可还原 binary64 的十进制表示，必要时记录原始位模式，以判断是否真同刻/同分。显示舍入只用于阅读，不覆盖原始证据。上述容差针对当前小实例，后续规模/单位变化时有记录地重新评估。

## 12. 轨迹最少记录什么

| 记录 | 最小字段/信息 |
| --- | --- |
